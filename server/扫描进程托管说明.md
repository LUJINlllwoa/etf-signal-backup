# scan_pm 常驻进程托管加固说明（2026-11-26，含重启实证）

## 背景
此前 scan_pm 由用户态 supervisord 托管，整机容器重启后保活进程一起被清，只能等看门狗定时探活补拉，
出现过十多分钟空窗。本次把扫描进程注册进系统级 supervisord，作为崩溃自愈的主挂接点。

## 当前托管层级（从主到兜底）
1. **系统级托管（主，崩溃自愈用）**：gem supervisord（`/opt/gem/supervisord.conf`，include `/opt/gem/supervisord/*.conf`）
   - 注册文件：`/opt/gem/supervisord/scan_pm.conf`（持久卷副本在 `bt_data/scan_pm.conf`）
   - 启动脚本：`bt_data/scan_pm_system.sh`（幂等单实例，防双开）
   - 程序：`scan_pm.py --loop`，user 身份，autorestart=true，startretries=999。
2. **用户态兜底（冗余）**：`scan_pm_supervisord.conf` + 看门狗 `--ensure`，系统托管失效或容器重启后由它被拉起。

## 防双开
- `scan_pm_system.sh` 检测到已有 `python3 scan_pm.py --loop` 则退出，不重复起。
- `ensure_daemon()` 先 `loop_running()` 探测，已有常驻就直接返回，不拉起用户态 supervisord。

## 自愈边界（已实测，2026-11-26）
- **脚本崩溃 / 被强杀**：系统托管几秒内自动重启（12:10 强杀 915 → 新 965，父进程 290 系统 supervisord，实测成立）。
- **整机容器重启：未自拉起（已实证失败）**。12:07 容器重启后，`/opt/gem/supervisord/scan_pm.conf` 被 rootfs overlay 重置清除，
  系统 supervisord 读不到该 program，scan_pm 没有随系统服务起来。

### 重启后根因排查（已逐项排除）
- rootfs 走 overlay，重启重置；`/opt/gem/supervisord/` 内用户新增文件丢失（镜像自带文件保留）。
- 另一套 include 目录 `/runtime/vm_supervisor/services/` 为 root 所有，user 不可写（Permission denied）。
- 容器内无 systemd、无运行中的 cron 守护、无 rc.local、无用户 autostart 目录；`/etc/profile.d` 不可写；
  登录 shell 的 `~/.profile`/`~/.bashrc` 不被 supervisord 托管进程读取。
- 持久卷仅 `/home/user`、`/sandboxdata/workspace`、`/sandboxdata/data` 等，系统服务不读取这些位置的注册项。
- 平台周期任务最短 1 小时（minExecInterval=3600s），无法做"停止即触发"的外部开关。

### 重启后实际恢复链路（当前唯一可靠通道）
平台侧 cron 看门狗（容器外调度，cron_job_id `18369946381058`，每小时 7 分）触发 `scan_pm.py --ensure`
→ 拉起用户态 supervisord → 拉起 `scan_pm.py --loop`。空窗长度取决于距下一个整点触发的时间。
每次手动/会话内重新装入系统 conf 后，崩溃自愈回到系统托管；重启后系统 conf 丢失，退回该兜底链路。

## 关键文件
- `bt_data/scan_pm.py`：主程序（`--loop` 常驻 / `--ensure` 看门狗 / 单次扫描）。
- `bt_data/scan_pm_system.sh`：系统托管自举脚本。
- `bt_data/scan_pm.conf`：注册到 gem supervisord 的 program 配置（副本；装入 `/opt/gem/supervisord/` 的那份重启会丢）。
- 备份：交接目录 `02_服务端/` 与 Git 仓 `server/`。

## 待观察 / 局限
- 该沙箱没有可写且重启保留的系统服务注册位置；整机重启后的空窗只能由平台 cron 看门狗兜底，受 1 小时最小间隔限制。
- 若后续平台开放持久自启钩子或可写的系统 include 目录，再把 scan_pm 挂到该位置，实现重启即拉起。
