# scan_pm 常驻进程托管加固说明（2026-11-26，含重启实证与兜底方案）

## 目标
scan_pm 常驻进程崩溃后秒级自愈；整机容器重启后尽快自动恢复，不依赖长间隔看门狗；
不破坏信号推送、复盘、云端同步链路，不改已锁定的生产策略参数。

## 当前托管层级（从主到兜底）
1. **系统级托管（主，崩溃自愈）**：gem supervisord（`/opt/gem/supervisord.conf`，include `/opt/gem/supervisord/*.conf`）
   - 注册文件：`/opt/gem/supervisord/scan_pm.conf`（持久卷副本 `bt_data/scan_pm.conf`）
   - 启动脚本：`bt_data/scan_pm_system.sh`（幂等单实例，防双开）
   - 程序：`scan_pm.py --loop`，user 身份，autorestart=true，startretries=999。
2. **用户态兜底（冗余）**：`scan_pm_supervisord.conf` + `--ensure`，系统托管失效或容器重启后被拉起。

## 防双开
- `scan_pm_system.sh` 检测到已有 `python3 scan_pm.py --loop` 则退出，不重复起。
- `ensure_daemon()` 先 `loop_running()` 探测，已有常驻直接返回，不拉起用户态 supervisord。
- `loop_forever()` 入口加独立单实例锁 `scan_pm.loop.lock`（flock 排他）：任何来源重复拉起第二个 `--loop` 直接退出，根治双开重复推送。
- watcher 自身单实例锁 `watcher.lock`，`--ensure` 与托管拉起互斥不双开。

## 自愈边界（实测，2026-11-26）
- **脚本崩溃 / 被强杀**：托管方几秒内自动重启（强杀 915 → 新 965，父进程系统 supervisord 290，实测成立）。
- **整机容器重启：容器内无法自拉起（已实证，见下）**。12:07 重启后 `/opt/gem/supervisord/scan_pm.conf`
  被 rootfs overlay 重置清除，系统 supervisord 读不到 program，scan_pm 没有随系统服务起来。

## 为什么容器内挂不了持久自启动（证据链）
### 1. 持久挂载点（仅这些重启后保留）
- `/home/user`、`/sandboxdata/workspace`、`/sandboxdata/data`、`/runtime/aio/app-data/browser/Default/customCookie`（hpvs_fs）
- `/tmp/user`（pmem ext4）
- 其余路径都在 overlay：lower=镜像层（只读铺回），upper=/run/kata-containers/.../snapshot/fs（重启随容器快照清空）。

### 2. 系统服务配置目录均不可持久注册
- gem supervisord include：`/opt/gem/supervisord/*.conf`（overlay，upper 新增文件重启丢失）。
- mcp-vm supervisord include：`/runtime/vm_supervisor/services/*.conf`（root 所有，700，user 不可写）。
- 两套 supervisord 本体配置（`/opt/gem/supervisord.conf`、`/etc/mcp-vm/supervisord.conf`）在镜像层，用户不可改。

### 3. 启动链不读取持久卷上的用户脚本（已逐段排查）
- init：dumb-init → runtime-agent `/opt/bytefaas/run.sh` → entrypoint.sh → 两套 supervisord。
- entrypoint：`vm_runtime_hook prepare-creation` → source `startup_env.sh` → exec supervisord；不跑用户脚本。
- gem.sh / run.sh / gem_init.sh / gem_env.sh / aio-cli-wrapper.sh / prepare-user-home.sh / browser-supervisor.py /
  python-server / jupyter / code-server / nodejs-repl：命令本体与配置均在 overlay 或镜像层，未 source/exec 持久卷脚本。
- 容器内无 systemd、无运行中的 cron 守护、无 rc.local、无用户 autostart 目录；`/etc/profile.d` 不可写；
  supervisord 托管进程不走 shell，不读 `~/.profile`/`~/.bashrc`。
- 持久卷内仅应用配置同步（输入法、skills、experience、应用 config），无可执行启动钩子。

### 结论
当前平台架构下，用户没有可控、持久、且被启动流程读取/执行的自启动入口。容器重启后无法在容器内自动拉起，
只能由容器外的平台定时任务触发 `--ensure` 补拉。

## 重启后兜底方案（已落地）
### 看门狗加密到 7–8 分钟一次（8 个独立 cron 错开分钟）
平台单任务最小间隔 3600 秒（1 小时），单任务无法设短周期；用多个独立 cron 错开分钟叠加兜底。
套餐定时任务上限 10 个（已用满：8 个看门狗 + 复盘 + m1 累积），无法再加密：

| 看门狗 | 表达式 | 说明 |
|---|---|---|
| E | `2 9-14 * * 1-5` | 每小时 02 分 |
| A（原常驻看门狗） | `10 9-14 * * 1-5` | 每小时 10 分 |
| F | `17 9-14 * * 1-5` | 每小时 17 分 |
| G | `25 9-14 * * 1-5` | 每小时 25 分 |
| B | `32 9-14 * * 1-5` | 每小时 32 分 |
| H | `40 9-14 * * 1-5` | 每小时 40 分 |
| C | `47 9-14 * * 1-5` | 每小时 47 分 |
| D | `55 9-14 * * 1-5` | 每小时 55 分 |

- 叠加节奏：每 7–8 分钟一次 `--ensure`（02/10/17/25/32/40/47/55，间隔 7、8 交替，最大 8 分钟）。
- 另有盘中 31 分任务第二步跑 `--ensure`（9:31/10:31/11:31/13:31/14:31/15:31/16:31）叠加兜底。
- 覆盖工作日 9-14 点（信号窗口 9:30-14:50）；午休 11:31–13:00 无交易不覆盖；14:50 收盘后看门狗不再空跑，15 点后仅由 15:31/16:31 盘中任务第二步 `--ensure` 兜底。
- 观察：新建看门狗首轮由平台调度器延迟加载（首轮时点可能跳过），次轮进入调度；`--ensure` 链路已手动验证（在跑则返回不双开，不在则拉起用户态兜底）。
- 2026-11-26 13:47 整机回收实证：空窗约 5 分 05 秒（等调度 4 分 56 秒 + 拉起 8.3 秒）；本次加密后同情况最坏等待压到约 8 分钟以内。

### ensure 拉起链路（重启后）
平台 cron 触发 `--ensure` → `loop_running()` 探测（在跑则返回不双开）→ 否则清理残留 pid/sock →
Popen 用户态 supervisord（`scan_pm_supervisord.conf`，在持久卷）→ 托管拉起 `scan_pm.py --loop`。
用户态 supervisord 同样 autorestart=true，崩溃秒级重启。

## 独立守护 watcher（2026-11-26 新增，外挂式守护）
### 为什么需要独立进程
scan_pm `--loop` 一旦崩溃/被回收，它内部线程一起死，无法自救。`scan_watcher.py` 是另一个
常驻进程，与主程序解耦，独立探活、独立订阅指令：
1. **周期探活（每 15 秒）**：识别 loop 进程在不在、心跳是否陈旧（>180s 判卡死）。
   - 不在 / 卡死 → 先 `supervisorctl start scan_pm`（覆盖兜底 program STOPPED/FATAL），
     再调 `scan_pm.py --ensure` 复用既有互斥与拉起链路。
2. **ntfy 指令订阅（后台线程，断线退避重连）**：订阅私有 topic，收到外部指令秒级动作：
   - `status` / `状态` / `健康`：回推 loop pid、心跳差到 ntfy。
   - `recover` / `拉起` / `重启扫描`：探活并拉起，回推结果。
   - 普通信号推送/状态回推不含指令词，不响应，避免回环。
3. **自身心跳** `watcher.heartbeat`、状态 `watcher_status.json`（watcher pid/心跳、loop pid/心跳差/是否卡死、检查时间）。

### watcher 托管与自愈
- 由用户态 supervisord（`scan_pm_supervisord.conf` 的 `[program:scan_watcher]`）autostart/autorestart 托管；
  watcher 崩溃由 supervisord 秒级重启（实测强杀 5104 → 4 秒内新 5353，成立）。
- watcher 自身也有 `--ensure`：不在则后台拉起（单实例锁防双开）。
- 边界：容器重启后 watcher 自身也消失，靠平台 cron `--ensure` 唤醒容器 → 用户态 supervisord autostart 一并拉起 scan_pm 与 watcher。

### 外部触发通道结论（已探查）
- 容器在 FaaS/NAT 后，无独立公网回调入口；平台网关 8080 路由锁定平台服务并带鉴权，挂不了自定义拉起接口。
- 能触达容器的外部触发：平台定时 cron（定时）；平台后端内部 API（鉴权、不可控）。GitHub Actions / 外部服务器等第三方定时器无入口触达容器。
- ntfy.sh 公网可达、可订阅，是当前唯一可复用的公网双向消息通道，watcher 据此实现"外部主动秒级触发"。
- 硬限制：没有外部常驻监控端的前提下，"自动发现死机"仍由看门狗定时兜底；watcher 解决外部主动触发，不替代外部监控。

### 止损判定口径修复（2026-11-26）
- 现象：信号推送与“跌破止损”相隔约 1 秒，刚触发就报止损。
- 根因：`track_positions` 止损判定用 `qt['low']`（腾讯 p[34]，当日累计最低），含触发前早盘探底的坑底低点；早盘砸过、下午反弹拉起的票，日内低点仍低于按反弹高点算的止损，刚触发同一轮即被误判 stopped。当日台账 6 只抽样在触发前已破止损 4~137 根 K。
- 修复：止损改为现价 `qt['now'] <= stop`（只看触发后现价），不再用日内累计最低；目标价 reached 判定本就走触发后 m1 K 线 + 现价，无此问题。
- 口径取舍：免费快照抓不到盘中插针瞬间，现价触价即走；旧台账已误判 stopped 的不复活，只对后续新信号生效。

### 大盘强弱口径（2026-11-26 对齐用户拍板）
- 基准：指数涨跌幅一律**对今日开盘价**（`now/open-1`），对齐个股 rt_open 口径；不再对昨收（高开回落的盘面会被昨收口径误判成红盘）。
- 三级状态：对开盘 ≤ -3% 判 crash（全停熔断）；≤ -1% 判 weak（走弱）；任一指数距日内最高点回落 ≤ -1%（`HIGH_PULL_PCT`）标记 `pullback` 回落段。
- **反弹启动（rebound，2026-11-26 新增）**：走弱/回落期间滚动记录各指数当日低点；现价从低点向上拉起 ≥ `REBOUND_PCT`（默认 0.3%）即判拐头向上、解除港股三类拦截，不必等站回最高点；跌回低点下方则下一轮重新拦截，回正后清低点。**crash 熔断不被 rebound 解除**。
- 港股环境开关 `is_hk_down_env()`：crash 硬停；否则 `(weak 或 pullback) 且非 rebound`。此环境下跟踪恒指/恒科的 ETF 反弹多为下跌中继反抽，**下午顺势、反转坑反弹、二次探底三类一律暂停**；指数每轮实时刷新，低点拐头拉起或站回高点后自动解除，无需手动恢复。
- 不在此开关范围：早盘锁定、低开高走早期（开盘首波，无充分高点参照，仅 crash 停）；美股 QDII（走隔夜美股）；商品期货 ETF（159980/159981/159985，走各自期货合约行情，`hk_index_tied()` 判定为 False，大盘走弱/回落时照常按自身量能触发，不随港股指数被拦）。
- 阈值常量：`INDEX_WEAK_PCT=-1.0`、`CRASH_PCT=-3.0`、`HIGH_PULL_PCT=-1.0`、`REBOUND_PCT=0.3`，均在 scan_pm.py 顶部，可调；大盘字段含 pct（对开盘）、high_pull（距高点）、rebound（反弹启动）、pull_low（回落滚动低点）。

## 局限 / 待平台开放项
- 容器重启后的空窗受平台 cron 调度节奏限制（当前 8 档兜底、最大约 8 分钟）；崩溃场景已是秒级自愈。
- watcher 把"外部主动拉起"做成 ntfy 指令通道；但容器重启后 watcher 自身仍需 cron 唤醒后由 supervisord 拉起。
- 若后续平台开放：可写且持久的系统服务 include 目录、容器内持久自启钩子、或外部"停止即触发"的 webhook，
  再把 scan_pm/watcher 挂到该位置，实现重启即拉起。
