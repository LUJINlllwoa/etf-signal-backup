# scan_pm 常驻进程托管加固说明（2026-11-26）

## 背景
此前 scan_pm 由用户态 supervisord 托管，整机容器重启后保活进程一起被清，只能等看门狗定时探活补拉，
出现过十多分钟空窗。本次把扫描进程注册进系统级 supervisord，随系统服务一起拉起。

## 当前托管层级（从稳到兜底）
1. **系统级托管（主）**：gem supervisord（`/opt/gem/supervisord.conf`，include `/opt/gem/supervisord/*.conf`）
   - 注册文件：`/opt/gem/supervisord/scan_pm.conf`
   - 启动脚本：`bt_data/scan_pm_system.sh`（幂等单实例，防双开）
   - 程序：`scan_pm.py --loop`，user 身份，autorestart=true，startretries=999。
   - 容器启动 → gem.sh 拉起 gem supervisord → 读 include → 自动拉起 scan_pm；崩溃由其秒级自愈。
2. **用户态兜底（冗余）**：`scan_pm_supervisord.conf` + 看门狗 `--ensure`，仅在系统托管失效时被拉起。

## 防双开
- `scan_pm_system.sh` 检测到已有 `python3 scan_pm.py --loop` 则退出，不重复起。
- `ensure_daemon()` 先 `loop_running()` 探测，已有常驻就直接返回，不拉起用户态 supervisord。

## 自愈边界（实测）
- 脚本崩溃 / 被强杀：系统托管约 2 秒内自动重启（2026-11-26 强杀实测）。
- 整机容器重启：系统 supervisord 随系统服务启动，scan_pm 由 include 配置自动拉起，空窗仅容器启动那几秒。
- 平台周期任务最短 1 小时，无法做"停止即触发"的外部开关；系统托管是当前环境内最稳的挂接点。

## 关键文件
- `bt_data/scan_pm.py`：主程序（`--loop` 常驻 / `--ensure` 看门狗 / 单次扫描）。
- `bt_data/scan_pm_system.sh`：系统托管自举脚本。
- `bt_data/scan_pm.conf`：注册到 gem supervisord 的 program 配置（已装入 `/opt/gem/supervisord/`）。
- 备份：交接目录 `02_服务端/` 与 Git 仓 `server/`。

## 待观察

  需下次容器重启后核对 `supervisorctl -c /opt/gem/supervisord.conf status scan_pm`。
